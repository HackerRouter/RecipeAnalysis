# ADR 0014：反编译源码的提交号由用户显式给出

- 状态：已采纳
- 日期：2026-11-01
- 相关：`inputs/manifest.toml` 的 `[source]` 段与各版本段、`src/oa/inputs/manifest.py`

## 背景

输入包需要记录反编译源码来自哪个提交，否则报告无法复算：同一标签的输入包换了一棵反编译源码树，两份报告的数字没有可比性。提交号因此是 provenance 的一部分，不是可选的缓存键。

提交号有两种取得方式：由用户写入配置，或由程序从反编译源码树所在的 git 仓库推导。后者只在「一个版本 = 一棵反编译源码树、工作树就是该版本」时成立；输入契约允许「一份独立的反编译源码仓 + 每版本指明提交」，此时 HEAD 与版本无关，推导必然出错。本决定取前者。

## 决定

`manifest.toml` 的每个版本段写 `content_commit`，由用户给出。程序不推导，也不提供推导开关。

## 换一种做法会错在哪

- **取 HEAD**：一个仓库带多版本历史是常见情形，工作树只停在其中一版。取 HEAD 得到的是「最后一次检出」的提交，与标签所指的版本没有必然关系。错误不会报出：导出结果看起来完整，报告照常产出，只是内容属于另一个版本。这类错误的排查成本远高于填写一行配置。
- **读 commit message 或 tag 匹配版本号**：各仓库的命名习惯不一，匹配规则只能覆盖见过的那几种。漏匹配时同样不报错，而是静默退回默认行为。规则越宽，误匹配越多；规则越窄，漏匹配越多，没有收敛点。
- **缺失时默认取当前工作树**：用户没有配置提交号时，最少惊讶的行为是记 `null` 并让 provenance 显式缺失，而不是补一个看似合理的值。缺 `content_commit` 的报告仍可读，但要在 provenance 中看出它不可复算。

## 判据

- 提交号只从配置读取。未配置则 provenance 记 `null`，不推导、不回退。
- 输入包只提供反编译源码树（`java/`）时，视为用户的第一手内容，同样记 `null`。
- 导出用 `git archive <提交>:<Java 源码根>`，不 checkout，不改工作树状态（见 [ADR 0013](0013-source-tree-by-feature-file.md)）。
- 提交号属于配置，写在 `inputs/manifest.toml` 的版本段；产物侧由 `output/<label>/run.json` 与 `oa guide` 的记录给出。

## 后果

- 加一个版本需要用户提供一行提交号。这是有意的负担：它把「哪个提交对应哪个版本」这条无法从数据推导的对应关系留在配置里。
- 换环境或换输入包时，未填提交号的输入会立刻以 `null` 暴露，而不是以错误的内容悄悄通过。
- 已产出的报告可以靠 `(jar 摘要, 方案版本, 提交号)` 三元组复算；缺其一即视为不可复算。
