# ADR 0013：反编译源码仓路径按特征文件定位，不按目录布局猜测

- 状态：已采纳
- 日期：2026-11-01
- 相关：`src/ra/inputs/source.py`、`src/ra/inputs/manifest.py` 的 `[source]` 段

## 背景

从提交里导出反编译源码时，必须先知道 Java 源码根在仓库的哪个位置——各类仓库的布局差别很大：
Gradle 工程是 `src/main/java`，裸导出是根下直接 `net/`，反编译产物带 `<版本>/src` 前缀，
多层组织是 `decompiled/26.3/src`。

最初的实现列了一张候选目录表逐个试探。这张表补不全：每遇到新布局就要加一行，漏加时
**静默失配**——探测不到就退回下一个候选，最终可能命中一个错误的、恰好含 `net/` 的旧目录。

## 决定

改用一个稳定的**特征文件**定位，读全量文件清单后找它的位置，前缀即 Java 源码根：

```
net/minecraft/WorldVersion.java
```

选择标准：每个版本都在且自 1.18 起位置未变；包名稳定，混淆产物里也是这个名字；语义上
就是「版本标识」，不会因重构被删或改名。

备用特征文件 `net/minecraft/SharedConstants.java` 在第一个未命中时再试。一次
`ls-tree -r --name-only` 读全量清单，比逐个试探目录少跑 git 进程，且对任何布局都成立。

## 不做的两件事

- **不读 commit message 或 tag 判断版本**：各仓库的提交习惯不一致——有的把版本号写在
  subject，有的写在 tag，有的什么都不写。按消息匹配等于把自己的约定强加给别人的仓库，
  一旦不符就静默取错。
- **不用 HEAD 推导**：一个仓库的工作树只停在一个版本，HEAD 只对应其中一份快照。拿它当
  某个版本的提交号会得到「看起来可信的错值」，比记 `null` 更糟。

## 逃生口

特征文件定位不到、或一个提交里有并列多份反编译源码树时，报错并列出候选，由用户在该版本段写
`source_path` 指定。**不静默取第一个**——那会分析错版本而毫无提示。

## 后果

- 不设 `SOURCE_CANDIDATES` 候选表，只用 `FEATURE_FILES`
- `find_source_paths()` 返回所有命中；`find_source_path()` 在多于一个时抛错
- 版本段新增可选键 `source_path`
- `tests/unit/test_source_layout.py` 钉住四种布局、并列多份、无反编译源码树三种情形
