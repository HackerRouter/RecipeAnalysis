# 数据包覆盖

分析对象是可运行的游戏配置，不是官方原版数据。玩家与整合包通过数据包替换配方、战利品表与标签，这些替换改变物品的获取路径。本决策规定覆盖如何算、结果放哪、下游读哪一份。

## 生成器不能代劳

数据生成器不读数据包，因此覆盖必须自己实现。

判据在反编译源码里：`net.minecraft.data.Main` 注册的 providers 全部从 `VanillaRegistries` 取注册数据，`--input` 只传给 `SnbtToNbt` / `NbtToSnbt` 两个结构转换器。它没有 `pack.mcmeta` 的概念，也没有「多个包按顺序叠加」的概念。

换一种做法的后果：

- **用 `--server --input <数据包根>` 当加载器**：该选项做的是 SNBT 转 NBT，不是加载。它会把输入目录当模板源重写，并在 palette 含重复空串时抛 `Multiple entries with same key`。得到的是被改写的模板，不是合并后的数据包。
- **用 `--reports` 反推数据包内容**：报告只覆盖代码侧注册表与默认组件，数据包内容不在其中。

生成器仍有两处用途，都不涉及覆盖语义：产出运行期导出，以及把模板 `.nbt` 升级并转成 `.snbt`。数据包带入的模板走同一条转换链，于是自动获得 `DataFixTypes.STRUCTURE` 升级。

## 合并语义照抄加载器

覆盖规则不按直觉定，按 `MultiPackResourceManager`、`OverlayedPackResources` 与 `TagLoader` 定：

1. **包内先叠加**：`overlays.entries` 里按当前格式版本筛出适用目录，每个目录是包内的一个子目录，其下同样有 `data/`。优先级是**包根 > 后列出的 overlay > 先列出的 overlay**。
2. 同路径资源整文件替换，后加载者胜。不做 JSON 深合并——游戏不做，深合并会产出双方都不存在的配方。
3. 标签文件按 `values` 追加到已有列表末尾。`replace: true` 先清空。最终成员按 `LinkedHashSet` 去重并保首次出现顺序。
4. `pack.mcmeta` 的 `filter.block` 屏蔽**比它低优先级**的包，`namespace` 与 `path` 各一个正则，语义是 `Pattern.asPredicate()`（部分匹配）。基底原版数据也在这条规则之下。

换一种做法的后果：

- **忽略 overlays**：多版本兼容包把每个版本的配方、战利品表、世界生成分别放在 `26_2_*`、`26_3_*` 目录里，包根可能只有一份占位或完全为空。忽略之后，分析结果与游戏里跑出来的不是一套数据，而且看上去完全正常。
- **全部 overlay 一律叠加**：把其它格式版本的目录也加进来，同样得到游戏里不存在的组合。必须按格式号筛选。
- **把 overlay 当成比包根优先**：`OverlayedPackResources` 的 stack 是「包根在最前，overlay 逆序跟随」，查找第一个命中者胜。反过来会让包根里那份“基础定义”被某个版本的补丁盖掉。
- **标签当整文件替换**：高优先级包只要改一个成员，其余成员全部消失，下游读到的标签比游戏里小。
- **把 filter 当可选优化跳过**：包用它删除旧配方时，被移除的配方仍会进入事实，形成游戏里已不存在却可获取的物品。
- **按正则整串匹配**：`path: "recipe/"` 这类写法在游戏里命中整目录，整串匹配下一条都不命中。
- **逐个文件深合并 JSON**：配方列表型字段会被拼接，得到游戏不认的形状。

## 顺序必须显式

加载顺序决定覆盖结果，因此写进配置：版本段的 `datapacks = [...]`，按低到高排。

- 目录里存在但列表里没有的包直接报错。静默跳过等于悄悄改动输入。
- 列表里写了但不存在的包直接报错。
- 未配置列表时按名称升序加载，并把这条回退写进 `notes`：结果可复算，但顺序不该由文件名决定。

## 生效数据根是唯一读入口

合并结果写入 `inputs/<label>/datapack-merged/`，其 `data/` 即生效数据根。探测与全部适配器都从 `Profile.data_root` 取它，不各自拼 `pack_data(pack_dir)`。

换一种做法的后果：新增适配器时忘了走合并路径，该族读的是原版数据，覆盖对它静默失效，而产物看起来完整。因此读入口只留一个，且由探测阶段写进 `Profile`。

台账的相对基准取数据根的父目录。两种情形下文件名都形如 `data/<ns>/...`，与无覆盖时的产物一致。

## 数据包会引入新命名空间

外来数据包很少只装 `minecraft`，自己带一个命名空间（`data/<包名>/worldgen/...`）是常态。因此探测阶段的两条假设都不再成立：

- **数据包目录锚点必须覆盖全部命名空间**。只取 `profile.namespaces[0]` 时，排序后正好是包自己的命名空间，`minecraft` 侧的注册表锚点整片丢失，标签归属退化成「按目录名」——表现是标签子目录从 `tag_dirs` 里一个个消失、台账冒出成片「没有适配器认领该文件」，而没有任何报错。
- **一个注册表目录只跟一份归属**。`Profile.dirs` 每个注册表取文件数最多的目录；包在另一个命名空间里也放了同族数据时，那份数据不进事实。台账会把它登记为「不参与推理」，不会静默消失。

换一种做法的后果：前者错得无声（覆盖率看上去仍是个数字），后者至少留了一行台账。

## 无数据包时不建目录
`inputs/<label>/datapacks/` 不存在或为空时，不生成合并目录，`Profile.data_root` 直接指向原版派生目录，`mode` 记 `identity`。

换一种做法的后果：始终复制一份，既有输入的产物全部漂移一次，磁盘多一份与 `data/` 等量的副本，缓存判据也要跟着改。分析原版时没有任何收益。

## 失败与留痕的分界

以下情形直接报错，不降级：

- 缺 `pack.mcmeta`，或 `pack.mcmeta` 含未实现的段。已实现 `pack`、`filter`、`overlays`。
- 格式号与原版不相容。游戏会把这类包标为不兼容；拿它分析得到的是另一个版本的数据。原版格式号取自 `version.json` 的 `pack_version.data_major` / `data_minor`（旧版为 `data`）；取不到时跳过校验并记 `notes`。
- 标签文件含 `values` / `replace` 之外的字段，或 `filter` 正则无法编译。
- `datapacks/` 下出现既非目录又非 `.zip` 的条目。

格式号是 `(major, minor)` 二元组。新式 `min_format` / `max_format` 可带 minor，旧式 `pack_format` / `supported_formats` 只有 major（minor 视为 0）；两者都认，新式优先。overlay 的适用判定同样用这个二元组——只比 major 会把 121.1 的包当成适用于 121.0。

以下情形继续执行并逐条留痕：

- 包内的非 `data/` 文件（如 `assets/`）不进入合并结果。数据包合并只作用于 `data/` 侧。
- 不适用于当前格式的 overlay 目录：逐文件登记为 `inactive_overlay`。
- 每个包文件在台账留一行去向：并入合并结果、被覆盖、被 filter 屏蔽、未生效 overlay、非数据内容、元数据。被覆盖与被屏蔽的副本不是「不存在」，否则「某条配方为什么没生效」无从查起。

## 边界

- 不处理资源包语义：`assets/` 只登记不入合并。
- 不模拟 Feature Flag：`data/<ns>/datapacks/` 下的内置实验包保持整棵排除，与游戏默认未启用的状态一致。
- 不推断顺序：没有 `level.dat` 可供读取，包顺序必须由使用方给出。
- 一个注册表目录只跟一份归属：`Profile.dirs` 每个注册表取文件数最多的那个目录。包在另一个命名空间里也放了同族数据时，那份数据不进事实（台账里登记为不参与推理），需要时另开 ADR 讨论多目录归属。
