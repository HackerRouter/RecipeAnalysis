# ADR 0009：产物口径与关系图表示

三类产物各有各的口径问题：可达率的分母取哪里，产物目录怎么分，以及关系图能不能脱离分析管道单独存在。

## 一、物品全集与可达率分母都取自注册表

候选来源有两个：运行期导出的 `registries.json` 的 `minecraft:item`，与 `assets/<ns>/items/*.json`。两者互相印证不上，只能留一个。

**`assets` 不是输入需求**：服务端 jar 内层只有个位数 `lang` 文件，没有 `items/`。要求用户提供 `assets/` 等于要求他从反编译源码树复制数千个文件，只为复现一次已经通过的等式检查。数据包里没有物品注册表，运行期导出是唯一能给出全集的途径。

`assets/` 仍作为可选输入：提供时逐文件登记台账，未提供不视为缺失。不设交叉校验函数——它唯一的用途就是被否决的第二途径。

**分母必须用注册表全集**，不能取「规则里出现过的 `item:` 节点」：没有规则的物品在规则图上根本不存在，会从报告里彻底消失。被隐藏的是刷怪蛋、`command_block_minecart`、`debug_stick` 这类零规则物品，报告上只表现为总数偏少，而总数偏少不会被察觉。

判据：`item_types` 缺省时取注册表的 `minecraft:item` 全集。`no_rule` 计入分母，归因统计覆盖全部物品。两版的具体偏差由 `ra guide --label <label>` 的「事实与规则产出」一节给出。

守卫：`test_universe_is_registry_not_rule_nodes`、`test_typed_only_not_in_denominator`、`test_item_universe_comes_from_registry`。

## 二、产物按层分目录

产物都落在 `output/<label>/` 下，但按层分目录，不平铺：

| 目录 | 内容 | 写它的命令 |
|---|---|---|
| `facts/` | 事实库：`<种类>.jsonl`、台账 `ledger.jsonl`、汇总 `summary.json` | `ra ingest` / `ra run` |
| `report/` | 可达性、覆盖率、`run.json`、缺口与工具要求明细 | `ra run` |
| `export/` | 下游可查表与 `exports.json` | `ra export` |
| `profile.json` | 探测结论：目录归属、方言、来源判定、输入 provenance（每版一份，放在产物根上） | `ra probe` / `ra ingest` |
| `graph.json` | 全量关系图的内部表示（核心产物，放在产物根上） | `ra graph` |
| `paths/` | `ra-paths` 的 `.dot/.svg/.html` 渲染件 | `ra-paths` |
| `guide.md` | 适配指南 | `ra guide` |

判据是「下游能不能只按目录取所需」：

- 平铺时下游只能按后缀 `*.jsonl` 取表，会把 `reachability` / `gaps` / `harvest` / `ledger` 一并拿走，再用文件名排除；排除表一漂就静默多读一类文件。
- 台账与汇总如果留在根上，「事实库」就散在两处；只读 `facts/` 的复盘与 `ra why` 会漏掉族级不可用与覆盖率。
- 渲染件与核心产物同层时，一份 `graph.json` 与它派生出的几十份副本混在一起，整目录同步的下游连可视化一起搬走；反过来把 `graph.json` 埋进子目录，下游又要多记一层路径。

因此下游只以 `export/` 与 `facts/` 为查表入口，其余目录是分析过程与可视化；`profile.json`、`graph.json` 与 `guide.md` 是每版各一份的产物，直接放产物根上。`ra-paths` 把渲染件写到 `--graph` 同级的 `paths/` 目录：视图跟着内部表示走，但不占据核心产物那层。

## 三、关系图：两条命令，中间一份文件

可视化最初是一次性脚本，每次运行都重建事实库、编译规则、重算不动点再渲染。两个问题：内部表示没有产物，外部消费者拿不到；建图与画图耦合，调一次画图参数就重算一遍。

```
ra graph --label 26.3                                    # 产物：output/26.3/graph.json
ra-paths --graph output/26.3/graph.json <物品 id>        # 视图：output/26.3/paths/ 下的 .dot / .svg / .html
```

`ra graph` 留在主命令下，因为它是管道产物。`ra-paths` 是**独立命令**，理由两条：职责不同（主管道每一步都是下一个的输入，可视化只是产物的消费者）；依赖不同（主管道不需要 Graphviz，独立之后缺 `dot` 的人仍能跑完整条链）。

`ra-paths` 只读内部表示，不碰 `inputs/`、不重算规则与不动点。

### 内部表示存什么

| 内容 | 为什么必须在文件里 |
|---|---|
| 规则（id / head / body / soft / kind / family / meta / prov） | 图就是它 |
| 三值状态（`true` 与 `unknown` 节点） | 判「这条规则画不画」靠它；只存规则的话，读回的人要么重新求解，要么瞎猜 |
| 种子 | 复算与追溯播种节点 |
| `graph_schema` / `ir_schema` / `facts_digest` | 产物可复算的凭据 |

缺席的节点按 `FALSE` 处理——这与 `SolveResult.of` 的语义一致，不是省略。

### 格式：单 JSON + 字符串表

字段原样落盘的体积主要浪费在同一个名字重复上千次（serializer、family）。字符串表加下标把体积减半，行序确定，仍可读可 diff。SQLite 随机访问好但不可 diff；msgpack / parquet 更快更小，但不可读不可 diff 且需装包。

写的 `newline="\n"` 与固定字段顺序让同一输入逐字节稳定。

JSON 的短板不是速度而是**不能随机访问**：取一个物品的路线要先把全部规则解析成对象。规则密度涨到需要随机访问时，`store.py` 的 `GRAPH_SCHEMA` 就是升级开关：换格式要 +1，`read_graph` 直接报错，不会静默读错。

### 不导出 PNG

SVG 已覆盖全部用途（矢量、可拖、可打印）。位图是体积远大于它的额外副本。

### 生成参数写进文字区，不写进图

| 规定 | 换一种做法会错在哪 |
|---|---|
| 只写文字区，不进图内标题 | 图内标题会随图缩放，而它恰恰是最需要看清的部分 |
| 写原始命令形式（`--expand-tags True`） | 译成中文就得维护一份只存在于展示层的词表；原文永远与 `build_parser` 一致 |
| 全量列出，不筛默认 | 图脱离命令行后，无从知道某个值是默认还是特意调的 |

把参数塞进文件名则一旦多于两个就没有可读性，且改名会破坏「同一输入产出同名文件」这个前提。

### 目标物品高亮

三重标记同时上：填充色 + 双层边框（`peripheries=2`）+ 加粗字号。只用颜色不行（色觉差异与黑白打印都区分不出）；只用形状也不行（形状在这张图里已有语义：菱形是规则、folder 是聚合）。

目标记在 `PathGraph.target` 而不是渲染参数上：同一个 `item:` 节点既可能是目标也可能只是中间原料，它是**角色**不是排序，不能放进按排序取值的 `FILL`。

### 全局起点不单独画

`world` / `assume` 是分析起点，不是来源。画成椭圆等于从一个点向几十个节点射出星形，既占版面又读不出「这个方块怎么来的」。

它们的边收进产物节点标签的第二行（`草方块 / 结构放置·废弃营地 · 主世界生成`）。反方向不可接受：

| 做法 | 错在哪 |
|---|---|
| 删掉起点边不做事 | 节点看着无源，读者以为它凭空可得；也违背「剪枝必须留痕」 |
| 把所有起点合成一个「世界」节点 | 几百个节点全连向它，图变成两团 |
| 连指向规则的菱形一起收 | AND 的一员被拿掉，规则就残了（交易 = 假设 + 付款物） |

### 战利品表的三条出路

`table:` 是「从哪拿」而不是「怎么来的」，不携带分支信息：

| 情形 | 处理 | 判据 |
|---|---|---|
| 表归属唯一来源 | 压成 `来源 → 产物` 边 | 只有一条入边 |
| 多张表出同一种产物 | 各成一条边，不合并 | 压出的边以表名区分，否则互相覆盖 |
| 预算用尽、表的入边没画 | 表名写进产物标签 | 零入边 |

零入边**不能直接删**：那是深度截断，删了就同时丢掉「这东西来自战利品」这条事实，而画面上又没有任何痕迹说明它被删了。指向规则的菱形时一律保留节点：菱形是 AND 的一员（挖矿 = 表 + 工具）。

## 换一种做法会错在哪

- **可视化直接读 `output/<label>/facts/`**：调用方必须知道「事实 → 规则 → 求解」这条链，还要跟着 `inputs/` 的路径走；而图本身与输入包无关，只与规则有关
- **内部表示不带状态**：判剪枝靠求解结果，不带状态就得在读回时重算，而读回的人手上没有种子与知识表
- **用 mtime 或文件摘要做缓存判断**：落盘加显式指定文件之后根本不需要缓存——过期就是一份旧文件，读它的人当场看得见 `facts_digest`
- **读到不认识的 `graph_schema` 尽力解析**：字段含义变了，半截解析会画出不存在的路径，且不报错

## 后果

- 一条命令产出内部表示，可视化可以换任意参数反复画，不必重算
- 主命令不含 Graphviz 依赖，缺 `dot` 不影响分析管道
- 全量关系图可跨版本 diff：两份 `graph.json` 的规则表直接对比即可看出机制变化
- `report/` 仍不读 `inputs/`：写内部表示在 CLI 层编排，建图与渲染都是纯内存函数
- 聚合逻辑（来源分类、同构识别、成员层上交）放在 `report/paths/` 而非 `solve/`，判据见 [`docs/development.md`](../development.md) 的分层硬约束
