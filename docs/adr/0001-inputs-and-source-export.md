# ADR 0001：输入包与反编译源码的导出

输入包由服务端 jar 与反编译源码两部分组成：jar 给数据包与注册表，源码给代码侧机制。源码从 git 仓库的某个提交导出，不 checkout、不改工作树状态。三处定位都不能靠猜——猜错时不报错，只让结论属于另一个版本。

## 一、源码根按特征文件定位

反编译仓库的布局差别很大：Gradle 工程是 `src/main/java`，裸导出是根下直接 `net/`，反编译产物带 `<版本>/src` 前缀，多层组织是 `decompiled/26.3/src`。

候选目录表补不全：每遇到新布局加一行，漏加时**静默失配**——探测不到就退回下一个候选，可能命中一个恰好含 `net/` 的旧目录。

改为读一次全量清单定位特征文件，其前缀即源码根：

```
net/minecraft/WorldVersion.java
```

选择标准：每版都在、自 1.18 起位置未变、包名在混淆产物里也稳定、语义上就是版本标识。未命中时试备用 `net/minecraft/SharedConstants.java`。

一次 `ls-tree -r --name-only` 比逐个试探目录少起 git 进程，且对任何布局都成立。

## 二、提交号由用户显式配置

提交号是 provenance 的一部分：没有它，同一标签的输入包换一棵源码树后，两份报告的数字没有可比性。

`manifest.toml` 的每个版本段写 `content_commit`，程序不推导，也不提供推导开关。未配置时 provenance 记 `null`，报告仍可读，但从 provenance 能看出它不可复算。

| 做法 | 错在哪 |
|---|---|
| 取 HEAD | 一个仓库带多版本历史是常态，工作树只停在其中一版。取到的是「最后一次检出」，与标签所指版本无必然关系，且不报错 |
| 读 commit message 或 tag 匹配版本号 | 各仓库命名习惯不同。规则宽则误匹配，窄则漏匹配，没有收敛点，失败时静默退回默认行为 |
| 缺失时默认取当前工作树 | 最少惊讶的行为是显式记 `null`，不是补一个看似合理的值 |

导出用 `git archive <提交>:<源码根>` 解到临时目录，不建工作树、`inputs/*/java.json` 记 `{repo, commit, source_path, files}` 作为失效键。无该 marker 的 `java/` 视为用户第一手内容，覆盖需显式 `--force`。

## 三、版本实测结论不入库

适配一个版本要两类知识：这一版的输入里哪些位置有数据、各自什么形状；以及凭什么这样认、认错会怎样。前者随输入变化，后者不会。

两类写在同一份文件里时，第一类会腐蚀第二类：数字过期后整份文件的可信度下降，而读者无法分辨哪些句子仍然成立。

| 内容 | 落点 | 入库 |
|---|---|---|
| 某版本的实测结论（目录归属、形状、文件数、未归属项、族级不可用） | `ra guide --label <label>` 渲染到 `output/<label>/guide.md` | 否 |
| 识别判据（找哪里、按什么形状、什么情况不能认） | [`docs/shapes.md`](../shapes.md) | 是 |

指南内容全部来自 `ra probe` 与 `ra run` 的既有产物，只做渲染，不新增探测逻辑。手写的版本文件不在必需品之列——它没有机制能发现过期，实测中出现过与产物不符且无法判断是文档写错还是口径不同的计数。

| 做法 | 错在哪 |
|---|---|
| 手写千行的版本基线文件 | 计数靠人工抄写与更新，错误不可检出；读者无法判断某句是否仍成立 |
| 只写判据、不给任何版本视图 | 读判据无法回答「这一版我手上的目录叫什么」，适配者每次都要重跑探测 |
| 让 `ra guide` 复述判据 | 判据因此在两处存在，改一处忘一处 |

判据文档按「位置 / 判据 / 边界」组织，不按版本分节；指南每节末尾指向判据的对应小节，判据不复制指南的结论。

仓库内文档不写随输入变化的数字（文件数、可达率、耗时、规模），需要时现场取。指南内的路径写入产物时，仓库内路径转相对并标记仓库根，仓库外只保留最后一级——上游目录名属于使用方的机器信息，与复算无关。
