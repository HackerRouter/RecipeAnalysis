# ADR 0011：结构布局白名单与台账三态

结构内部布局要向采集侧提供「允许出现什么」，采集侧再按运行期实测给出「实际有几个」。两件事必须分开，否则静态推断会替代实测。

## 一、结构布局只出身份与白名单

数量取决于拼图运行期拼了几段，数据包给不出。能给出的只有身份：这个结构允许哪些模板、模板里有哪些容器与方块。

三张数据包侧的表再加一张代码侧的表：

| 表 | 一行是 | 回答的问题 |
|---|---|---|
| `structures` | 一个拼图结构 | 允许出现的模板、权重、拼装深度上限 |
| `template_containers` | 一个容器方块实体 | 哪些战利品表可能出现在哪个模板里 |
| `template_blocks` | 一个方块状态 | 结构专有方块有哪些，各几格 |
| `structure_containers` | 一个结构类型上的容器绑定 | 没有模板的结构在生成代码里挂哪张表 |

不合成一份 JSON：四张表的查询单位不同（结构、模板内的容器、方块状态、结构类型），合成后任何一次按模板过滤都要先走完整棵树；分开后每行自带主键，可直接 diff 两个版本。

**「上限」不预测实际拼装**：`size` 是拼图深度上限，权重是候选池内的相对值。两者只能做「实测不得超出白名单」的校验，不能反推「一个结构里有几个箱子」。

**池到模板是传递闭包**：结构只给起始池；池内模板的拼图方块还会引用别的池。只展开一跳会把村庄的房屋与街道漏掉，表看起来非空但覆盖不全。

## 二、拼图关系必须先进事实

`report/` 不读 `inputs/`，所以 `start_pool`、`size`、池内 `elements` 必须由适配器写进世界生成事实。缺任何一项，导出表只能靠重新解析输入包取得——那是把语法层复制到报告层。

池内 `list_pool_element` 的嵌套成员摊平后标 `nested`：嵌套元素的权重以它所在列表为分母，与顶层不是同一个分母。混算权重和会让「权重上限」偏大。

## 三、模板 ID 与容器来源都要能 join 上

**模板 ID 取模板根之后的全部路径。** 模板可以含与根目录同名的子目录（`ancient_city/structures/barracks`），按目录名再切一次会得到裸名 `barracks`，与结构、池里的引用完全对不上——表里看着有容器，join 时全部落空。判据：拼图元素 `location` 去掉命名空间后必须与某个模板 ID 精确相等。

**带表的方块不一定在模板里。** 处理器可以把某格方块换成可疑沙 / 砾石，并附上战利品表（`block_entity_modifier: append_loot`）。这些容器只存在于 `processor_list` 与池元素的 `processors` 字段里，模板 NBT 中一个字节都没有。只从模板导出会让这类结构的容器数为零：不是没有容器，是找错了地方。

导出表因此区分容器来源：

| `via` | 坐标 | 数量上界 |
|---|---|---|
| `template` | 模板内坐标 | 模板里出现的次数 |
| `processor` | 无坐标 | 处理器的 `capped.limit`，每片段最多几处 |

`limit` 只能当上界：它是「本次应用最多替换几处」，实际命中取决于被替换方块是否存在与概率，仍需采集侧实测。

**容器在模板里不等于表在模板里。** 船骸、末地城、庄园的箱子在模板 NBT 中有坐标与 `Items`，却没有 `LootTable`——表由生成代码在运行时挂上。只导出有表的容器会让这些结构在表里整族缺席，「没有容器」与「表不可见」混为一谈。这类行保留坐标，`table` 为 null 并带 `loot_bound: "code"`。

**模板里没有不等于代码里没有。** 下界要塞、要塞、废弃矿井完全由拼装器代码生成，数据包里没有模板可枚举，容器与坐标都在代码里；海底神殿同样没有模板，但它在本版**连表都没有**——数据包里无 `chests/monument`，`BuiltInLootTables` 也没有对应常量，拼装器代码不挂表。后者不产行不是缺口，是「真的没有容器」。这类由第四张 `structure_containers` 接管，见下节。

## 四、代码侧容器绑定单独一张表

没有模板的结构（下界要塞、要塞、废弃矿井）与「模板里有箱子、表由代码挂上」的结构（船骸、末地城、庄园、雪屋），表都在拼装器代码里。这张表回答「哪个结构能出哪个容器、哪张表」；海底神殿没有可挂的表，因此不出行。

**结构 id 从数据回连，不从类名猜。** 类名与结构 id 不一一对应（`OceanMonumentPieces` 对应 `monument`，`WoodlandMansionPieces` 对应 `mansion`）。可靠的三跳全在代码里：

1. `StructureType.register("<id>", <类>.CODEC)`（26.x）或 `StructureFeature.register("<id>", new <类>(...))`（1.18.2）给出结构类型 id → 结构类
2. 结构类正文引用的 `*Pieces` / `*Piece` 类名（必须在索引里真实存在）
3. 拼装器类正文里 `BuiltInLootTables.<常量>` 所在的语句，按调用名分类容器形态

结构 id 由世界生成事实的 `type` 回连（结构 JSON 的 `type` 就是注册的那个 id），所以 `structures` 字段来自数据包与代码两边对上，而不是拼出来的。

**为什么不是 `code_link`。** 这些绑定不描述「物品怎么获得」，只描述「容器在哪」。进 `code_link` 会被编译层当成可达性规则，`holds` 更会被当成表别名（`bridge/table_provider` 就收 `head` 以 `table:` 开头的 `holds`），把两张无关的表桥到一起。所以单独立一种事实，只给导出表用，不进求解。

`sites` 是同一绑定在该文件里的调用点个数，**不是每个结构实例的箱子数**：拼装器按房间反复调用，实际数量取决于拼装结果。采集侧同样只能当上界用。

## 五、台账有第三种状态

事实有 `parsed` / `partial` / `failed` 三态，台账只有两态，缺项文件只能记成 `parsed`。后果是「有产出但缺项」与「完整产出」在台账上不可区分，覆盖率也把它们算成一样。

`partial` 进入台账后必须带 `missing`，与事实的构造校验一致。覆盖率把 `partial` 算作「有产出」：文件确实读出了事实，只是字段不全，把它计入失败会让覆盖率下降掩盖真实缺口。

流浪商人的交易组是首个用例：它们不按等级划分，`level` 无法确定。下游按（职业, 等级）索引时会落空，必须在台账与事实两处都能看到原因。

## 换一种做法会错在哪

- **把四张表合成一份嵌套 JSON**：按模板查容器要遍历全部结构；跨版本 diff 会因整体结构变化而读不出单条增删。
- **用类名推结构 id**：`OceanMonumentPieces` 与 `monument`、`WoodlandMansionPieces` 与 `mansion` 之间没有可复算的映射，猜出来的 id 会造出假节点。
- **把容器绑定写成 `code_link`**：会被当成可达性规则，`holds` 还会把两张无关的表桥接起来。
- **只导出起始池**：村庄只有 `town_centers` 一个池，房屋与街道全部缺失，白名单校验会把大量实测容器判成「超出上界」。
- **靠报告层重新读 `inputs/`**：破坏分层，且导出表会与事实脱节——事实更新而表未更新时无人能发现。
- **台账只记 `failed` 之外的两种状态**：缺项文件看起来和完整文件一样，正是红线 3 要防的静默跳过。
- **`partial` 不计入覆盖率**：覆盖率下降会被误读成解析退化，实际只是字段不全。

## 后果

- `ra export --label <L>` 产出四张 JSONL 与一份 `exports.json`（label、事实计数、各表行数）。
- 采集侧可以用白名单做上界校验：实测的容器表或方块不在白名单内即为异常。
- `ledger.jsonl` 的状态值增加 `partial`，`facts-summary.json` 的覆盖率各节增加同名计数。
