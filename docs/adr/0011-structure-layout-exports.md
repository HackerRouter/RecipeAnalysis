# ADR 0011：结构布局白名单与台账三态

结构内部布局要向采集侧提供「允许出现什么」，采集侧再按运行期实测给出「实际有几个」。两件事必须分开，否则静态推断会替代实测。

## 一、结构布局只出身份与白名单

数量取决于拼图运行期拼了几段，数据包给不出。能给出的只有身份：这个结构允许哪些模板、模板里有哪些容器与方块。

三张表分工：

| 表 | 一行是 | 回答的问题 |
|---|---|---|
| `structures` | 一个拼图结构 | 允许出现的模板、权重、拼装深度上限 |
| `template_containers` | 一个容器方块实体 | 哪些战利品表可能出现在哪个模板里 |
| `template_blocks` | 一个方块状态 | 结构专有方块有哪些，各几格 |

不合成一份 JSON：三张表的查询单位不同（结构、容器、方块状态），合成后任何一次按模板过滤都要先走完整棵树；分开后每行自带主键，可直接 diff 两个版本。

**「上限」不预测实际拼装**：`size` 是拼图深度上限，权重是候选池内的相对值。两者只能做「实测不得超出白名单」的校验，不能反推「一个结构里有几个箱子」。

**池到模板是传递闭包**：结构只给起始池；池内模板的拼图方块还会引用别的池。只展开一跳会把村庄的房屋与街道漏掉，表看起来非空但覆盖不全。

## 二、拼图关系必须先进事实

`report/` 不读 `inputs/`，所以 `start_pool`、`size`、池内 `elements` 必须由适配器写进世界生成事实。缺任何一项，导出表只能靠重新解析输入包取得——那是把语法层复制到报告层。

池内 `list_pool_element` 的嵌套成员摊平后标 `nested`：嵌套元素的权重以它所在列表为分母，与顶层不是同一个分母。混算权重和会让「权重上限」偏大。

## 三、台账有第三种状态

事实有 `parsed` / `partial` / `failed` 三态，台账只有两态，缺项文件只能记成 `parsed`。后果是「有产出但缺项」与「完整产出」在台账上不可区分，覆盖率也把它们算成一样。

`partial` 进入台账后必须带 `missing`，与事实的构造校验一致。覆盖率把 `partial` 算作「有产出」：文件确实读出了事实，只是字段不全，把它计入失败会让覆盖率下降掩盖真实缺口。

流浪商人的交易组是首个用例：它们不按等级划分，`level` 无法确定。下游按（职业, 等级）索引时会落空，必须在台账与事实两处都能看到原因。

## 换一种做法会错在哪

- **把三张表合成一份嵌套 JSON**：按模板查容器要遍历全部结构；跨版本 diff 会因整体结构变化而读不出单条增删。
- **只导出起始池**：村庄只有 `town_centers` 一个池，房屋与街道全部缺失，白名单校验会把大量实测容器判成「超出上界」。
- **靠报告层重新读 `inputs/`**：破坏分层，且导出表会与事实脱节——事实更新而表未更新时无人能发现。
- **台账只记 `failed` 之外的两种状态**：缺项文件看起来和完整文件一样，正是红线 3 要防的静默跳过。
- **`partial` 不计入覆盖率**：覆盖率下降会被误读成解析退化，实际只是字段不全。

## 后果

- `ra export --label <L>` 产出三张 JSONL 与一份 `exports.json`（label、事实计数、各表行数）。
- 采集侧可以用白名单做上界校验：实测的容器表或方块不在白名单内即为异常。
- `ledger.jsonl` 的状态值增加 `partial`，`facts-summary.json` 的覆盖率各节增加同名计数。
