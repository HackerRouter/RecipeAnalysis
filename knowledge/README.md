# knowledge/

分析所依赖的领域知识。求解器不内置任何常识，全部知识在此声明。

## 收入判据

一个事实若能由程序从输入取得，就不写在这里：

| 事实来源 | 落点 |
|---|---|
| 数据包 JSON、服务端 jar 的运行期导出 | `src/ra/adapters/` |
| 反编译源码中形态固定的写法 | `src/ra/adapters/source/idioms/` |
| 以上均不可得 | `knowledge/` |

进入本目录的是只写在行为代码里、且各条写法互不相同的机制（掉方块、放入物品实体、
替换手持物、改方块状态、孵化）。形态不固定，无法归纳成统一提取器，只能逐条声明并给出取证位置。

## 结构

目录名即分类，不靠文件名前缀区分。

```
knowledge/
  assumptions.toml      立场：分析所站的前提
  maps/
    vocabulary/         词汇：枚举值到求解器概念的映射
    mechanism/          机制：具体游戏机制
    exceptions/         例外：生存确定不可获取
```

### 立场

不是事实，是分析前提。每条带 `survival` 开关：置为 `false` 可观察去掉该前提后
多少物品转为不可达。同时作为不动点求解的播种节点。

独居根下而不入 `maps/`：它不是某类数据表的映射，而是整个分析的出发点。

### 词汇

数据中的枚举值到求解器概念的映射：战利品条件的判定类别、配方序列化器的工艺设备、
工具类对应的物品集合。这类表把数据中的取值翻译成求解器的条件。

### 机制

具体机制。每条带 `basis`（一行依据）与 `evidence`（可复算的代码位置或数据包路径）。
相邻机制的边界写在各自文件内，与内容同处，不在此处重复。

### 例外

生存确定不可获取的物品。前三类参与规则编译，本类参与归因：把 `no_rule` 拆分为
「确定不可获取」与「机制尚未提取」。判据与字段见文件内说明。

## 校验强度

漏登记一条的后果按「是否改变可信判定」而定：

- **硬失败**：词汇类中决定硬前置的部分（条件类别、工艺设备）。未登记若默认成
  「无前置」，会把需要设备或条件的物品误判为可得。
- **记录后继续**：机制类与工具类。漏一条则该机制产出的物品落 `no_rule`，
  报告会指出，已覆盖部分仍可信。
- **退化不报错**：例外表。缺它时 `no_rule` 不区分类别，归因仍完整。

## 读取方式

`src/ra/ir/compile.py` 是唯一读取方，分类目录名以常量 `VOCABULARY` / `MECHANISM` /
`EXCEPTIONS` 出现。`assumptions.toml` 与 `maps/` 全部在 `compile_ir` 开头一次性读入，
各编译阶段只接收数据。例外表由 `src/ra/cli.py` 读取，因其属于归因层而非规则层。

路径由 `src/ra/paths.py` 的 `knowledge_*` 系列给出，不在各处拼字符串。

`solve/` 与 `report/` 不读取文件。这些目录出现文件访问即为分层失效。

各表以 `_` 开头的键为说明或私有数据（`_about`、`_patterns`），不参与匹配。
